# Знай цену — Адаптивный анализатор цены: исследовательский план
Дата: 26.11.2026. Статус: согласованное направление, не утверждение о внедрении. Ветку v47 и утвержденную плашку не изменять ради экспериментальных зависимостей.

## Базовый механизм
- При достоверном полном маршруте Яндекса — его км, адаптивный вес ETA Яндекса и BRouter; проверенная денежная надбавка: 0–499: 0.5; 500–999: 0.6; 1000–1499: 0.8; от 1500: 0.9. Это гипотезы, спрос не равен пробкам. При неизвестной надбавке текущий код использует 0.7 (проверить как отдельную гипотезу). Если один источник отсутствует, использовать валидный другой. Показанная цена заказа имеет приоритет, не прибавлять надбавку повторно.
- Не использовать остаток маршрута и подачу как полный пассажирский маршрут; учитывать все подтвержденные промежуточные точки. Не генерировать км по прямой или фиксированное время из 30 км/ч.
- Официальные ставки проверить по актуальной дате; исторический справочник не выдавать за актуальный. Измерять отдельно фиксированную цену при принятии и итоговую стоимость/доплаты.
- Для каждого заказа фиксировать до принятия чистые прогнозы Яндекса/BRouter, гибрид, исходные км/мин, вес, источник, качество адресов и версию тарифа/карты/модели. После принятия прогноз заморозить; итоговый факт отдельно. Не оценивать ретроспективный расчет как предсказание.

## P0. Устранить ошибки адресов до машинного обучения
Источники:
- https://www.sqlite.org/fts5.html — префиксный и trigram поиск; проверить доступность в системном SQLite на API 29/34/36.
- https://github.com/openvenues/libpostal — нормализация адресов; серверный/сборочный эталон, не тащить большую модель в APK без замеров.
- https://github.com/pelias/interpolation — оценка расположения пропущенных номеров по форме улицы; не маркировать как точный адрес.
Порядок: перебор всех вариантов PlaceLookup, name/name:ru/name:kk, альтернативные названия и транслитерация, дом/корпус/дробь отдельными полями, индексы кандидатов, географическая проверка, отказ при неоднозначности. Проверить выбор первой/последней строки и ложные совпадения. Тесты на независимой выборке адресов Алматы; precision/recall, отказ вместо неверной точки, p95, размер индекса. Не сохранять пассажирские адреса в общей базе.

## P1. Коллективная дорожная статистика
Источники:
- https://github.com/graphhopper/graphhopper/tree/master/map-matching — HMM привязка GPS к реальным дорожным ребрам; идентификаторы графа меняются при обновлении PBF.
- https://github.com/valhalla/valhalla/blob/master/docs/docs/concepts/historical-traffic.md — временные профили направленных ребер, недельные интервалы по 5 минут.
- https://github.com/valhalla/valhalla/issues/6112 — привязка скоростей к версии графа.
- https://github.com/uber/h3 — зональная статистика спроса; не заменяет дорожное ребро.
- https://github.com/abrensch/brouter/issues/937 — проверить направленные ограничения maxspeed на закрепленной версии BRouter.
- https://groups.google.com/g/osm-android-bikerouting/c/MjlXZaHVCIw — публичное обсуждение поиска участков с отсутствующими дорожными атрибутами.
Пилот: добровольный GPS с контролем точности/скорости и направления, локальная HMM-привязка к ребрам; агрегировать скорость, число независимых наблюдений, разброс и давность. Начать с 30–60-минутных периодов, 5 минут только при достаточной плотности. Отбрасывать стоянку вне поездки, плохой GPS, скачки и невозможные скорости; дорожные задержки учитывать отдельно. Граф/версия карты обязательны. В облако отправлять только минимальные агрегаты без маршрутов/адресов/личных данных; пороги публикации, защита от повторов и отравления, ограничение хранения, согласие, правовая проверка места хранения данных Казахстана. Supabase — существующий отдельный проект; не обещать бесплатность при масштабе. Офлайн кэш агрегатов с TTL, при отсутствии откат на BRouter.

## P2. CatBoost: два разных предиктора
- https://github.com/catboost/catboost
- https://github.com/catboost/tutorials/blob/master/apply_model/model_export_as_cpp_code_tutorial.md
- https://github.com/catboost/catboost/blob/master/RELEASE.md
- https://habr.com/ru/companies/yandex/articles/344954/
- https://habr.com/ru/companies/yandex/articles/431196/
Модель A — поправка ETA BRouter/гибридного ETA, признаки: исходные км/мин обоих источников (пропуск отдельно), день недели/час, дорожный профиль, наблюдаемые скорости, доля главных дорог, повороты, погода если законно доступна, надбавка как слабый индикатор спроса. Цель — фактическое время пассажирской поездки; не обещать точность цены через фактическое время.
Модель B — поправка к базовой цене при принятии, отдельно по тарифу и подтвержденным дополнительным начислениям; надбавка добавляется один раз. Итоговый чек и фиксированная цена — разные цели. Не обучать по оценкам самой модели.
Сначала простая регуляризованная модель и медианные поправки; CatBoost только если улучшение на новых поездках. Обучать вне телефона, экспортировать числовую компактную модель C++/проверенный Android applier; измерить размер, время, RAM и расход батареи. Без сети локальная модель. Подписанная версионная модель и схема признаков, откат на v47, запрет обновления без валидации; неизвестный тариф/адрес — безопасный fallback.
Валидация по времени (train earlier, test later), группировка по поездке/водителю, одинаковая выборка для сравнения всех моделей; минимум MAE KZT, медиана и средняя относительная ошибка, p90, доля <=5%/10%, покрытие, ошибки по тарифу и наличию полного badge, по времени суток и спросу. Отдельно latency p50/p95. 30 поездок — пилот, недостаточно для заявления о точности CatBoost. Цель 3–5% — не обещание.

## P3. Дополнительные эксперименты
- https://github.com/Mobile-Artificial-Intelligence/atlas — способ изготовления офлайн rd5 из векторных тайлов на устройстве (проверить лицензии, совместимость, качество OSM тегов и стоимость упаковки).
- https://github.com/mikhail-angelov/2maps-and — пример MapLibre + встроенный BRouter без внешнего приложения; проверить лицензии и подходы к упаковке.
- https://github.com/yandex/mapkit-android-demo — официальные примеры routing/offline. Не извлекает закрытый маршрут Яндекс Про. Использовать только после проверки договора, ключа, условий, бюджета и разрешенного сценария; не использовать закрытые ключи, обходы или автоматическое управление Яндекс Про.
- https://gitlab.com/explore/projects/topics/openstreetmap — дополнительный каталог, не утверждение о найденном готовом решении.
- https://groups.google.com/g/osm-android-bikerouting/c/WW6tZR42o-Q — исторический кейс расходящейся длительности; проверить собственный профиль и источник ETA, не переносить чужие ошибки на текущую версию.
Проверить GPL/MPL/Apache и ODbL каждой конкретной зависимости и данных до копирования исходников, закрепить версию. Цель: не добавлять платных зависимостей в базовый режим.

## Порядок реализации и приемки
1. Собрать и проверить v47 отдельно; исправить блокирующие ошибки, оставить внешний вид без изменений.
2. Адресный benchmark и разбор ошибок, затем исправления.
3. Сбор независимой статистики на реальных заказах; экспорт обезличенных метрик.
4. Map matching + локальные/коллективные профили, сравнение с исходным BRouter.
5. CatBoost в теневом режиме, сравнить с простыми моделями; включить только после выигрыша и замеров на Android 10/14/16.
6. При ухудшении вернуться к предыдущей модели. Не утверждать, что исследования уже внедрены или обеспечивают пробки в реальном времени.
